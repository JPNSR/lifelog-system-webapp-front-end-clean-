### 1. 位置づけと設計思想（なぜ作ったのか）
#### ① プッシュ型（Discord）から「プル型（探索室）」への拡張
日々の運用において、Discordは「今起きたこと」「毎晩のアーカイブ」をリアルタイムに受け取る**プッシュ型のストリーム通知**を担っています。しかし、過去数ヶ月〜数年分の思考の変遷を俯瞰したり、特定の概念がどのように結びついているかを辿るには、チャットツールのUIでは限界があります。
Webappは、蓄積された膨大なライフログを能動的に掘り起こし、自己の認知パターンや知的資産を多角的に観察するための専用のプル型ビューア（探索環境）として設計されました。

#### ② Write（収集）と Read（閲覧）の完全分離
GASはバックグラウンドでの自律的なデータ収集・正規化・DB書き込み（Write）に徹し、人間が利用する閲覧・分析インターフェース（Read）を完全にフロントエンドへ切り離しています。これにより、UI側の改修や機能追加がデータ収集パイプラインに一切影響を与えない堅牢な疎結合を実現しています。

#### ③ 閲覧専用（Read-Only）とデータ保護の徹底
本アプリは「純粋な閲覧専用」として構築されており、データの追加（INSERT）や更新・削除（UPDATE/DELETE）を行うコードやUIは意図的に排除されています。
* **Anon Key（読み取り専用）の強制と検証:** フロントエンドにはSupabaseの公開用キー（`anon`）のみを入力させ、強力な権限を持つ `service_role` キー等が誤入力された場合はクライアント側のJWT検証（`validateAnonKeySafety`）で弾く安全装置を備えています。
* **カラムホワイトリスト（`STRICT_TABLE_SCHEMAS`）:** `select('*')` を全面的に禁止し、テーブルごとに必要なカラムのみを指定して取得。音声全文文字起こし（`raw_transcript`）などの重い生テキストや内部UUIDは初期ロード対象から除外し、通信量とブラウザメモリを保護しています。

#### ④ 「思考の摩擦」をそのまま残すUI/UX哲学
* **事実とAI解釈の視覚的並置:** 1日のタイムラインにおいて、「客観的事実・数値」と「AIによる深層メタ認知洞察（`metacognitive_insight`）」や「筋トレのAIフィードバック」を色分けして並置します。タスクのリマインドや催促は行わず、日々の「未解決の問い・構造的摩擦（`unresolved_frictions`）」をありのままに提示します。
* **誠実なNULL表示（`renderNullOrText`）:** 記録がない生体データや項目について、勝手に `0` や空文字で埋めず、「記録なし（NULL）」として正直に表示します。

### 2. 技術スタックとアーキテクチャ

* **アーキテクチャ:** 単一HTML（Single-File SPA）によるノービルド（No-Build）構成。
* **スタイリング / レンダリング:** Tailwind CSS（CDN）、marked.js（Markdown描画）、DOMPurify（XSS防止サニタイズ）。
* **ホスティング:** GitHub Pages（無料静的ホスティング対応）。
* **PWA（Progressive Web App）化:** `manifest.json` と Service Worker により、Android / iOS のホーム画面に追加して全画面ネイティブアプリ感覚で起動可能。
* **モノレポ構成（`lifelog-system/Webapp/`）:**
* GASのバックエンドスクリプトと同じリポジトリで管理。
* `.claspignore` に `Webapp/` を明記することで、GAS（`clasp push`）への混入を防止。
* Google Antigravity IDE ＋ Supabase MCP により、データベースのスキーマ変更時にバックエンドとWebappの表示コードを一括でAIエージェントに同期・修正させる運用体制を確立しています。

### 3. 主要機能と画面構成
Webappは主に**3つのビュー ＋ 詳細インスペクター**で構成されています。
```
┌─────────────────────────────────────────────────────────────┐
│ Webapp「セカンドブレイン探索室」                             │
├───────────────┬────────────────────────────┬────────────────┤
│ 1. ナレッジグラフ │ 2. 統合タイムライン       │ 3. クロス検索   │
│ (共起ネットワーク)│ (JST日次ストリーム)       │ (エクスポート) │
├───────────────┴────────────────────────────┴────────────────┤
│ [詳細パネル / Record Inspector] (クリックしたログの深掘り表示) │
└─────────────────────────────────────────────────────────────┘

```
#### ① ナレッジグラフ（タグ共起ネットワーク）
* **思考の結節点の可視化:** `tag_dictionary` のタグと、日次ログ（`semantic_keywords`）や音声トピック（`tags`）に付与されたタグ同士の「共起関係（同じ日に一緒に使われた関係）」をノードとエッジで描画します。
* **毛玉化（ヘアボール問題）対策:**
* 通常時は共起回数2回以上（`GRAPH_COOC_DEFAULT_MIN_WEIGHT = 2`）の太いエッジのみを表示し、視認性を維持。
* 特定のノードをクリックした際のみ、重み1の潜在的エッジを破線（`stroke-dasharray`）で展開し、思考の文脈を深掘り可能。
* **フロントエンド名寄せ:** 過去データに存在する `#VS Code` と `#VSCode` のような表記揺れを読み込み時に自動除去（`replace(/\s+/g, '')`）し、1つの統合ノードとして集計。
#### ② 統合タイムライン（日次ストリーム）
* **JST自動補正:** Supabaseから取得したUTC基準の `TIMESTAMPTZ`（`created_at`, `shot_at`, `start_time` など）をブラウザ側で日本標準時（Asia/Tokyo）へ正確に変換。
* **マルチソースの日次束ね:** 対象日（`record_date`）ごとに、デイリーサマリー、音声インサイトカード、写真（食事PFCや情景描写）、トレーニング実績、ヘルスケアデータ（睡眠・歩数・HRV）を1本のタイムラインとして綺麗に統合・可視化します。
#### ③ クロス検索 ＆ エクスポート
* 過去ログ全体を対象としたキーワード検索。
* 除外カラム（UUIDや内部座標など）をサニタイズした上で、整然としたJSONまたはCSV形式でクリップボードやファイルとして安全にエクスポート可能。
#### ④ 詳細ドロワー（Record Inspector）
* タイムラインやナレッジグラフ上のカード・ノードをクリックした際に開き、AIが解析した長文の思考プロセス、比喩表現、身体コンテキストなどをじっくり読み込める専用ドロワー。

### 4. 泥臭いエンジニアリングと耐障害性
1. **`Promise.allSettled` による部分障害の許容:**
* 10個前後のテーブル（`daily_logs`, `voice_insights`, `health_logs` 等）を並列フェッチする際、開発中・未整備のテーブル（例: `location_logs`）がHTTP 404や空データを返しても、UI全体がクラッシュすることなく「取得できたテーブルのみで正常に画面を描画」するフォールバック設計。
2. **スキーマ差異の吸収:**
* `health_logs` の歩数カラム名の差異（仕様書上の `step_count` と実DBの `steps`）をフロントエンドのクエリスキーマ側で吸収し、HTTP 400エラーを未然に防止。
3. **フェッチ上限（limit）の制御:**
* 1時間おきに蓄積されて肥大化しやすい `digital_activity_logs` などに対し、クエリ段階で取得件数制限を設けることで、Supabaseのデフォルト1,000件上限やブラウザの描画負荷を制御。

## 1. 概要とアーキテクチャ

* **配置場所**: `lifelog-system/Webapp/index.html`（単一ファイルSPA構成）
* **役割**: Supabaseに蓄積されたライフログ（`daily_logs`, `voice_insights` 等）を、安全な読み取り専用（`anon` キー使用 / `GET` のみ）で可視化・横断探索するフロントエンド。
* **開発・運用方針**: バックエンド（GAS / Supabase）のスキーマ変更時は、Webapp 側のHTML（[`STRICT_TABLE_SCHEMAS`](index.html)）も同時に更新し、システム全体のバージョンを一致させる。
* **設計意図**: 過去の蓄積データを自発的に「探索・振り返り」するためのプル型ビューア（タスク催促・通知による強制を排した純粋な観察環境）。

## 2. セキュリティ・データ誠実性の設計方針

本アプリケーションは **完全に「閲覧専用（Read-Only）」のアプリケーション** として設計されています。

* **書き込み機能の完全排除**: データを追加（`INSERT`）や更新・削除（`UPDATE` / `DELETE`）するコードやUIは一切存在しません。
* **権限の制限（安全装置）**: Supabaseに接続する際、読み取り専用の公開キー（`anon` キー）のみを受け付け、万が一強力な権限を持つキー（`service_role` キーや `sb_secret_` キー等）が入力された場合はフロントエンド側で自動的に拒否する安全装置（`validateAnonKeySafety`）を実装しています。
* **取得カラムのホワイトリスト化（`select('*')` の完全禁止）**: テーブルごとに必要なカラムだけを厳密に指定して取得し、文字起こし全文（`raw_transcript`）やシステム内部ID、生JSON、GPS座標などの除外対象カラムはクエリに含めません。
* **耐障害性（`Promise.allSettled`）**: 全10テーブルを並列取得する際、未作成のテーブルや権限対象外のテーブルが存在してもアプリ全体が停止せず、取得できたテーブルのみで画面を構築します。
* **プレースホルダー初期設定**: コード内の `APP_CONFIG` はプレースホルダー（`YOUR_SUPABASE_PROJECT_URL` / `YOUR_SUPABASE_ANON_KEY`）となっており、初期状態では外部通信を行わず内蔵の架空サンプルデータ（全10テーブル・計42件）で安全に動作します。

## 4. 本稼働・接続セットアップ手順（全4ステップ）

### Step 1: Supabase側の読み取り権限（RLS）の確認

Supabaseのデータベースで、対象テーブル（`daily_logs`、`voice_insights` 等）に対して `anon` ロールでの `SELECT`（読み取り）が許可されているか（Row Level Security の設定）を確認します。

### Step 2: 接続情報の設定（2通りの方法）

以下のいずれかの方法で Supabase プロジェクトに接続できます。

1. **画面上のモーダルから接続（推奨・コード変更不要）**
   * ブラウザで `index.html` を開きます（初期状態はサンプルデータモードで起動します）。
   * 画面右上の **「クエリ仕様・接続設定」** ボタンを開き、`Supabase Project URL`（`https://<YOUR_PROJECT_ID>.supabase.co`）と `Anon Key` を入力して **「Read-Only接続を試行 (GETのみ)」** をクリックします。
2. **`index.html` 内のプロパティ定数（`APP_CONFIG`）で設定（個人ローカル環境向け）**
   * `index.html` 内の `<script>` 先頭にある `APP_CONFIG` オブジェクトのプレースホルダーを書き換えます。
   ```javascript
   const APP_CONFIG = Object.freeze({
     SUPABASE_URL: "https://<YOUR_PROJECT_ID>.supabase.co",
     SUPABASE_ANON_KEY: "<YOUR_SUPABASE_ANON_KEY>"
   });
   ```
   > **注意**: 公開リポジトリ（GitHub等）へ Push する際は、必ずプレースホルダー（`YOUR_SUPABASE_PROJECT_URL` / `YOUR_SUPABASE_ANON_KEY`）の状態に戻してください。

### Step 3: 実データ表示の動作確認

ナレッジグラフ、統合タイムライン、クロス検索＆JSON/CSVエクスポート画面で実データが正しく表示されることを確認します。

### Step 4: 静的ホスティング（GitHub Pages 等）での公開

バックエンドサーバーを必要としない単一HTMLファイル（SPA）のため、GitHub Pages・Vercel・Cloudflare Pages 等の無料ホスティングサービスでそのまま配信できます。

#### GitHub Pages の設定手順例:
1. 変更をコミットし、`git push` で GitHub リポジトリ（`<YOUR_USERNAME>/lifelog-system`）へ反映します。
2. GitHub リポジトリ上部の **Settings ➔ Pages** を開きます。
3. **Source** を `Deploy from a branch`、**Branch** を `main`（フォルダは `/ (root)`）に設定して **Save** します。
4. 数分後、`https://<YOUR_USERNAME>.github.io/lifelog-system/Webapp/` のURLが発行され、PCやスマートフォンのブラウザからアクセス可能になります。
　※スマートフォン部分はまだ開発中です
